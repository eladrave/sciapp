# Care journal and local-time reminders (0.11.3)

## Reminder behavior

The backend compares UTC instants, then formats clocks in the account IANA timezone. `careAgenda` returns the local clock, today's unconfirmed occurrences, the next future task, and active routine medications without explicit times. At 09:30 in America/New_York on November 9, 2026, the 11:30 catheter task is upcoming. Notification permission does not gate the agenda or in-chat check-ins.

`get_care_agenda` returns the authoritative schedule reply directly. The model selects the tool from ordinary language; it does not have to infer task status by comparing UTC clock strings with local HH:mm values. The UI shows a check-in after messages and refreshes it each minute while the conversation or Today page is visible and idle. Refreshes do not interrupt the journal, draft text, settings, an open dialog, an active medication selection, or a pending care review.

Medication occurrences have distinct IDs and are grouped by their scheduled local time. Each group lists its medicines with three actions: Took them all, Took only some, and Not yet. All asks the actual time once. Some provides large checkboxes, then asks one shared actual time. One concrete review covers the whole group. Approval records each actual time and `scheduledFor` separately and suppresses only the taken occurrences. Unselected medicines are explicitly reviewed and recorded as not taken yet, remain unconfirmed, and their chat check-in returns after 30 minutes. All rows and stock settings are validated before any group writes; approval replay is idempotent. Individual records support correction/undo. Unknown stock consumption units do not block recording a reported dose; the review explicitly leaves stock unchanged. Reminders never establish dose completion or recommend catch-up doses. The 30-minute chat snooze stores a reminder preference, not a dose record, and requires an open page or subsequent return to show again. PRN medications have no routine reminders.

## Accessibility and voice

Minimal required hand movement is a product requirement recorded in `AGENTS.md`, not an optional UI setting. Ask one essential question at a time and reuse already supplied facts. Use short contextual suggestions and large controls; support voice/text for the same actions. Grouped check-ins use one timing question and one approval instead of repeating them for every medicine.

The native `medication_checkin` tool and `POST /api/medication-checkin` share a bounded, account-owned workflow. Its active question expires after 30 minutes, but an interrupted reported selection can be resumed for the same unchanged daily medication occurrences. Completed or changed occurrences cannot be reused. Resuming asks only for missing timing or reopens the existing pending review, with no duplicate proposal or care writes. UI answers carry a check-in ID and revision so old buttons cannot change a later question. Ordinary speech can report all, some, named medicines, numbered selections, or all except a medicine. If a time is already provided, the tool resolves it and proceeds directly to a review. Touch and voice do not require the user to repeat the same facts in different formats. Unsaved checkbox drafts survive re-renders; later voice/text turns include the current selection as validated conversation context. The server checks its workflow ID, revision and owned medicine IDs before using it. Drafts never record care or change stock. Different actual times must not be collapsed into an invented shared time.

Conversation check-in cards are suppressed while answering a focused care question or reviewing a proposal. Interrupted medication reports expose a compact Continue action, also available by voice, preserving already reported medicines. Connected browsers do not show empty or future-only cards. Hide for 30 minutes snoozes current due occurrences without changing care records, stock or schedules; newly due care can still appear.

Dismiss beside a medication or care reminder hides only its occurrence from the chat agenda and push dispatcher. Today retains a dismissed label for that occurrence. The native `dismiss_reminders` tool and `POST /api/reminders/dismiss` validate account-owned occurrence IDs; ambiguous spoken targets require a clarification. Dismissal is prompt state, never a taken/skipped clinical event, stock mutation or recurring schedule change. Occurrence keys are schedule-version specific and short-lived dismissal metadata is pruned on subsequent dismissals.

Chat following tracks user reading intent separately from layout changes. The scroll controller observes both the viewport and conversation content, including delayed photo/card sizing and the working indicator. Scrolling up preserves the reading position; new submitted turns return to the latest reply.

## Photo capture time

JPEG EXIF APP1, PNG eXIf and WebP EXIF can supply `DateTimeOriginal` and `OffsetTimeOriginal`. The bounded parser reads only those time fields and their EXIF directory pointer; it does not extract GPS data. Original image bytes remain intact. Missing or damaged metadata returns no capture time. Metadata is editable and a camera clock may be wrong, so the review always labels its source and asks the user to verify it.

A valid camera offset produces an absolute capture timestamp. Without an offset, the account timezone is an explicit assumption, re-evaluated if that timezone changes. Future camera timestamps are not automatically usable. `resolve_care_time` supports `photo_capture` and returns an opaque time reference plus its caveat. An explicit user correction takes priority. The app retains original capture time, upload time and the approved care observation time separately. Screenshots and messaging apps may omit original capture metadata; upload time must never stand in as proof of capture time.

## Push notifications

The browser requests permission from a direct Enable button before network or Permissions API awaits. An already-denied permission cannot display another native prompt; the app now says that explicitly instead of claiming all Chrome or Android notifications are blocked. Chrome 155+ on Android uses a non-blocking notification prompt, which can return default after timing out. Instructions explain Expand all requests and site-specific permission reset, plus the separate Android app permission when SCIapp is managed as an installed app. Device registration follows permission and service-worker subscription. Account-scoped endpoint checks detect a missing server registration and reconnect an already-authorized browser. The conversation exposes setup when this browser is disconnected. Browser or Android permission denial must be changed on that device.

The Worker push fetch uses `redirect: manual`, rejects unsuccessful responses, and retains the FCM/Mozilla/Apple host allowlist, encrypted generic payloads, occurrence deduplication, retries, and expired-endpoint cleanup. No health details appear on the lock screen. Medication and catheter schedules use the same minute dispatcher.

### Notification setup diagnostics

`POST /api/push/diagnostics` records only whitelisted technical states in D1 `push_setup_diagnostics` (migration 0010). Reports are scoped to the signed-in account and a random browser ID. Fields include notification and Permissions API states, setup phase, whether requestPermission was called, user activation at that call, subscription presence, secure/top-level/standalone flags, Chrome major version, request duration, and sanitized error class. No endpoint, credential, full user agent, photo, care record, or arbitrary error text is stored. Each browser/phase retains its latest state; retention is bounded to 60 phase rows per account. Diagnostics failure never blocks permission or registration and does not modify the care ledger/account version.

A new client reports status once per changed permission/connection state. Enable records blocked-before-request, requested, result, service-worker, subscribing, registering, ready and sanitized failure phases as applicable. A pending opt-in survives a denied/dismissed prompt so granting it later in Site Controls can reconnect automatically. A screenshot of global Chrome notification settings alone cannot establish SCIapp's actual permission or the precise Android layer blocking it.

## Persistent journal

Original image bytes remain in the private per-account R2 namespace. Image metadata, vision evidence, and user text are saved alongside the account's care ledger; confirmed events link the original photo ID. The previous 100-photo preview cap applies only to anonymous previews. Signed-in users retain originals until explicit deletion. Raw voice recordings are not retained; submitted transcription text is part of the conversation.

`occurredAt` is the observation/administration time. `createdAt` is when the record was saved. BP/pulse, medication doses, bag readings, catheterization, and journal notes support distinct occurrence times. Historic records without an occurrence timestamp fall back to their original creation timestamp; an earlier time cannot be reconstructed from missing evidence.

`POST /api/journal` searches the complete account ledger, not only the last 15 events shown in AI context. Filters include category, inclusive local start/end dates, today/yesterday, images only, and inclusion of corrected records. Queries use the account timezone and an exclusive start of the day after the requested end date, including DST transitions. Results are newest first, with a maximum of 50 entries per request and stable cursor pagination. Image queries deduplicate repeated records about the same original. Unlinked images are explicitly unreviewed; deleted originals remain unavailable while the care record is retained.

`query_care_journal` normally renders matching records and original image cards directly in chat. `purpose: lookup` permits reading identifiers or values before another action or analysis. Lookup results include server-formatted local timestamps; the model must not convert UTC clock strings itself. All lookups are read-only and account scoped. `journalNote` prepares a reviewed user observation with a resolved occurrence time, category, and optional owned photo. AI appearance estimates remain separate from user observations and are not diagnoses.

History provides category/date filters, original image viewing, comparison of up to three images, correction visibility, and a PDF-only doctor report. One Download doctor PDF action generates and downloads an application/pdf file locally. The HTML download and browser-print alternatives were removed. Each unique original photo receives its own full-page view, with portrait or landscape orientation chosen to fit. JPEG/PNG source pixels are retained without thumbnail downsampling; rotated JPEGs and WebP are converted losslessly to upright PNG at their decoded dimensions. Notes remain selectable text using a locally bundled Unicode font. Long notes paginate, deleted/unavailable originals are explicitly labeled, and repeated references to the same image share one full-page photo. Load additional pages before preparing a larger report. Reports are generated in the browser and are not sent to anyone. Account JSON export includes care data and photo metadata, not original image bytes.

## Storage boundary

This release searches the existing persistent account ledger rather than introducing a separate clinical database. Image bytes are stored separately in R2, but account metadata and care events still share the account JSON record. A future storage migration should move journal rows and photo metadata into indexed per-account tables before sustained high-volume use approaches D1's row/value limits. The API pagination contract is designed to remain stable through that migration. This release does not establish a clinical archive retention SLA or validate urine appearance as a medical measurement.

## Bag photos and scheduled catheterizations (0.11.5)

A catheterization takes time and its bag photo is taken afterwards, so a record no longer has to fall within 90 minutes of the scheduled time to count. A catheterization record counts for the latest scheduled daily occurrence that started up to three hours before it. If none did, it counts for an occurrence starting within the next 90 minutes. Each record completes at most one occurrence, and records are matched in time order. With a 7:00 AM schedule, a record at any time from 7:00 to 10:00 completes the 7:00 occurrence. Interval reminders are unchanged: any confirmed catheterization restarts the interval.

When a photo is sent with no other request, the image is identified as a urine bag with a readable amount, no review is pending, and the photo time matches a still-unconfirmed occurrence, the server prepares one catheterization review without a model call and without asking whether the catheterization was done. The photo time is the camera capture time when the image carries one (with the existing camera-clock and timezone caveats); otherwise the upload time is used and labelled in the review. The review states which scheduled time it counts for. Nothing is saved, no catheter is deducted and the check-in keeps asking until the review is approved. Time and amount can still be corrected by button or in conversation.

The fast path is skipped, and the conversation handles the photo as before, when the user typed anything with the photo, the amount is unreadable, the camera timestamp is in the future, the photo already has an approved entry, another review is pending, or the time is not near a scheduled occurrence. In the conversational path the same server-computed match is supplied to the model as `photoEvidence.scheduleMatch`.

Not validated: live vision accuracy of the amount on real bags, and behaviour on a physical phone. The matching and review logic is covered by `test/catheter-photo-match.test.js` with synthetic data.

## Conversation length (0.11.5)

The conversation renders only the latest ten turns, so it opens on the newest message instead of laying out the whole history and scrolling down. A See earlier messages control at the top adds ten older turns at a time, keeps the turn being read in place, keeps keyboard focus on the control and announces the change. Sending a message or receiving a reply returns to the latest ten. This also limits how many saved photos are fetched on each render. Covered by `test/browser/scroll.spec.js`.
